# C0 集成设计与风险

**日期：** 2026-10-28\
**范围：** C0 集成设计、C1 宿主与启动安全\
**基线：** `main` / `edb3bcc`

## 1. 项目与依赖

```text
QuickNotes.Desktop.Wpf (net10.0-windows, WinExe, UseWPF)
  -> QuickNotes.Desktop.Core (net10.0, no WPF)
       -> QuickNotes.Application
       -> QuickNotes.Infrastructure.Sqlite
       -> QuickNotes.Infrastructure.Drafts
       -> QuickNotes.Infrastructure.Backup
       -> QuickNotes.Domain
QuickNotes.Desktop.Tests (net10.0)
  -> QuickNotes.Desktop.Core
```

- Domain/Application 不引用 WPF 或 Desktop。
- WPF 只做窗口/命令/展示；业务组合、单实例、启动状态机、重建和持久阻断在 Desktop.Core。
- 桌面层不直接执行 SQL；保存/恢复/写入门仍通过 Application 契约。
- 不搬迁 A 原型；C1 新建宿主，A 的托盘/窗口模式留 C5。

## 2. 数据目录与日志

```text
%LOCALAPPDATA%\QuickNotes\                 # 默认数据根；--data-root 覆盖
├─ notes.db                                 # 当前权威数据库（schema v1）
├─ application-state.json                   # 初始化标记/写入阻断/恢复记录
├─ recovery-journal.json                    # 恢复阶段日志（C1 识别，C4 写入阶段）
├─ drafts\                                  # FileNoteDraftStore（C2 接入 UI）
├─ logs\quicknotes-yyyyMMdd.log             # 诊断日志，不含正文
└─ .quicknotes-recovery-<guid>\             # 缺失库重建临时目录
```

- 备份目录 C1 不配置；`--backup-dir` 仅用于诊断扫描保护快照/临时产物。
- 测试与手动验收使用临时数据根；不访问真实用户目录。
- 日志字段：UTC 时间、级别、事件名、错误码/摘要；不记录便签正文/草稿内容。

## 3. 启动流程

```text
App.OnStartup
  -> 解析 --data-root / --backup-dir / --single-instance-probe
  -> 计算数据根
  -> SingleInstanceGuard.StartAsync（数据根锁文件 + Named Pipe；第二实例不打开数据）
  -> DiagnosticLog
  -> ApplicationStateStore.ReadAsync
  -> RestoreJournalStore.ReadAsync
  -> StartupArtifactScanner.Scan
  -> StartupCoordinator.StartAsync
       -> 首次初始化 / Ready / NeedsRecovery / WriteBlocked / ReadOnlyDiagnostic
  -> StartupWindow（最小诊断/恢复入口）
  -> 退出时释放单实例/管道/Mutex
```

单实例所有权必须先于：打开 `notes.db`、创建草稿目录、启动后台备份/调度任务。

## 4. 启动状态机

| 输入 | 模式 | 动作 |
|---|---|---|
| 无状态 + 无 DB/草稿/恢复产物 | FirstRunInitialized | 写 `Initializing` → schema 初始化 → 校验 → 写 `Ready`；失败不写 Ready |
| 状态 Initializing + 无 DB/无证据 | ReadOnlyDiagnostic | 提供“重试初始化”，不自动建库 |
| 状态 Ready + DB 缺失 | NeedsRecovery | 不建空库；提供选择已验证备份重建 |
| 状态 Ready + DB 损坏/不兼容 | NeedsRecovery | 保留原库；诊断/手动选择备份；不自动覆盖 |
| 状态存在 + `-wal`/`-shm` | NeedsRecovery | 不删除 sidecar；说明 WAL 不支持 |
| 状态缺失 + DB/草稿/恢复产物存在 | ReadOnlyDiagnostic | 不初始化、不删除；说明需人工确认 |
| 状态 JSON 损坏/未知版本 | ReadOnlyDiagnostic | 保留状态文件；不猜初始化 |
| `writesBlocked=true` | WriteBlocked | 只读诊断；**重启不自动清除** |
| 恢复日志未完成（非 Completed/Failed） | NeedsRecovery | 保留 staging/保护/回退；不猜恢复来源 |
| 恢复日志损坏/未知版本 | ReadOnlyDiagnostic | 保留；不清理/不猜来源 |
| 其他 + DB 可准备/检查 | Ready | `PrepareCurrentAsync` 恢复热 journal；失败转 NeedsRecovery |

所有失败路径只记录/展示错误，不删除当前数据库、保护快照、回退副本或 sidecar。

## 5. 单实例

- 第一实例在数据根 `.quicknotes-instance.lock` 上以 `FileShare.None` 持有排他句柄；锁在打开数据库/草稿/后台任务之前取得。
- 命名管道 `QuickNotes.Activate.<data-root-hash>` 用于激活；第二实例未取得锁句柄时不打开数据资源，连接管道发送 `ACTIVATE`。
- 成功则第一实例激活；超时/无管道则明确提示“已有实例但无法激活”并退出。
- 选择锁文件而不是命名 Mutex：Mutex 线程亲和/可递归，异步启动/退出与同进程测试不可靠；锁文件跨线程/跨进程语义稳定，OS 在崩溃后释放句柄。
- 第二实例在任何数据打开前退出；不写日志/状态/数据库。
- C1 提供 `--single-instance-probe` 仅用于真实第二进程测试，不创建窗口/不打开数据库。

## 6. 恢复日志与恢复产物

`recovery-journal.json`（C1 建立契约/读取；C4 在真实恢复各阶段写入）：

```json
{
  "formatVersion": 1,
  "restoreId": "guid",
  "stage": "Staging|ProtectionCreated|Switching|Verifying|Rollback|Completed|Failed",
  "currentDatabasePath": "...",
  "stagingDirectory": "...",
  "protectionSnapshotPath": "...",
  "rollbackPath": "...",
  "startedAtUtc": "...",
  "updatedAtUtc": "..."
}
```

- 未完成阶段 → 启动进入 NeedsRecovery，保留关联路径。
- 损坏/未知版本 → ReadOnlyDiagnostic；不按文件名/时间戳猜来源。
- 恢复产物扫描（`.quicknotes-restore-*`、回退库、保护快照、`.quicknotes-tmp-*`、`.quicknotes-package-*.tmp`）在 C1 **只识别、默认保留**，不自动删除。
- 清理只在能证明归属、引用关系、当前库和恢复状态后执行；C1 不做自动清理。

## 7. 缺失库重建

```text
用户选择已验证备份 ZIP
  -> 当前库存在且有效：拒绝（C4/B5 恢复路径）
  -> 当前库损坏：需用户确认，隔离为 quarantine
  -> 同卷 staging 提取 + B3 完整校验
  -> Inspect schema=1/完整性/外键/counts
  -> 当前库缺失：File.Move(staged, current)
     当前库损坏：File.Replace(staged, current, quarantine)
  -> 重新校验当前库 SHA-256 = manifest + schema/counts
  -> 写 Ready/恢复记录
  -> 失败：保留 staging/quarantine，不报成功
```

无当前库时明确记录“未创建保护快照”，不得伪造保护成功。

## 8. 持久写入阻断

- `PersistentDatabaseWriteGate` 包装既有 `DatabaseWriteGate`。
- `BlockWrites()` 先原子写 `application-state.json.writesBlocked=true` 与原因/时间，再置内存阻断；状态写失败记录错误但仍在内存阻断。
- 启动读到 `writesBlocked=true` 进入 WriteBlocked；不因重启/重建服务对象清除。解除必须由后续验证/恢复入口显式执行（C4/C6）。

## 9. 线程与生命周期

- 启动/恢复/重建使用 async/await；不在 UI 线程同步等待数据库、管道或快照。
- UI 命令执行期间禁用相关按钮；异常转为 UI 错误 + 日志。
- `ShutdownMode=OnMainWindowClose`；退出释放单实例/管道/日志。
- C1 无托盘/快捷键；关闭诊断窗口即退出。

## 11. 性能候选预算（待确认，不作为 C1 通过标准）

- 数据量：1,000 张历史便签；5/10/20 张可见窗口。
- 启动到 Ready（无 UI）p95 ≤ 2s；含窗口显示 ≤ 3s。
- 正常保存提交 p95 ≤ 500ms，p99 ≤ 1.5s；BUSY 最坏按 B2 ADR 约 3.4s。
- UI 输入响应 ≤ 100ms（C2 验证）。
- 20 窗口 + 1,000 历史工作集 ≤ 300MB（C6 验证）。
- 备份/恢复耗时在 C6 按实际数据库规模记录，C1 不承诺。
- 设备：AMD Ryzen 7 8845H（8C/16T）、约 15.3 GiB RAM、C: SSD（C0 实测环境）；其他设备需重测。

## 12. 风险清单

| 风险 | 级别 | 处理 |
|---|---|---|
| A-11 多显示器断开找回失败 | 高（C5） | C5 专项修复与多屏矩阵；C1 不宣称解决 |
| 首次运行/状态缺失误建空库 | 高 | 只有无任何数据证据才初始化；否则只读诊断 |
| 单实例激活失败/竞态 | 高 | 锁文件先于数据；管道超时明确退出；真实第二进程测试 |
| 持久阻断写失败 | 高 | 原子写状态、失败日志；C6 真实故障验证 |
| 缺失库重建与 B5 分叉 | 中 | 只走无当前库路径；C4 统一安全边界 |
| UI 线程阻塞 | 中 | async 启动/重建；C2 细化保存状态 |
| 恢复产物误删 | 高 | C1 只保留；清理需证明归属/引用 |
| 人工 UI 不可自动化 | 中 | 人工清单；未运行如实记录 |
| WPF/多屏/DPI 未验证 | 中（C5/C6） | A 历史不能替代 C 验收 |
