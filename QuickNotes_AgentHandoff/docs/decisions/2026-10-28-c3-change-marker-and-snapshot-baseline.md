# ADR：C3 持久化变更标识与备份成功基线

- **日期：** 2026-10-28
- **状态：** 已接受（随 C3 实施记录）
- **范围：** 确定性变更检测、`database_meta` 序号、快照内变更标识、成功备份基线、恢复/迁移身份轮换
- **相关：** `docs/agent/Agent对接文档_C阶段.md` C3/C4、PRD 11.2、11.5、11.8、15.2、[B4 留存与变更检测 ADR](2026-10-28-b4-retention-and-change-detection.md)、[B3 快照与包格式 ADR](2026-10-28-b3-consistency-snapshot-and-package.md)、[C3 字段策略 ADR](2026-10-28-c3-schema-v2-field-strategy.md)、[C3 迁移与恢复兼容 ADR](2026-10-28-c3-migration-and-restore-compatibility.md)

## 背景

B4 使用启发式 SQL 指纹判断“数据是否有变化”，存在分类/标签同长度重命名等漏检风险。C3 要求所有应备份内容的写入与变更标记在同一事务提交，包括分类/标签重命名、关系、外观和应用设置；成功备份基线必须对应包内实际快照的标记，不能在快照生成后读取更新的源库标记，否则会把未包含的新编辑当作已备份。恢复/迁移后若沿用相同序号，旧基线可能与新数据碰撞。

## 决策

1. **单一持久化变更标识**
   - 新增 `database_meta` 单行：`database_id`（GUID）与 `change_sequence`（非负整数）。
   - `database_id` 标识数据库身份；`change_sequence` 在身份内单调递增。
2. **同事务更新**
   - 任何写入应备份内容的事务（`notes`、`note_tags`、`categories`、`tags`、`app_settings`）必须在提交前递增 `change_sequence`。
   - 事务回滚不得保留序号变化；读操作不递增。
   - 便签与设置保留各自乐观锁 `version`；分类/标签在 C3 采用单写者假设，不加版本列，后写覆盖（用户已接受该候选局限，C5 前保持单管理窗口）。
3. **变更身份替代启发式指纹**
   - 备份调度比较持久化的 `(database_id, change_sequence)` 基线，而不是重新计算 SQL 指纹。
   - 同长度分类/标签重命名、颜色/字号/布局修改、关联变化、应用设置变化都会递增序号，不再漏检。
4. **快照内读取标记**
   - 备份使用 SQLite 一致性快照生成 `notes.db` 后，从**快照库本身**读取 `database_meta` 作为该包的变更标识。
   - 不得在快照生成后读取源库并获得“更新”的序号；快照期间新增编辑未包含在包内，必须保持为待备份变化。
   - `SnapshotInfo.Marker` 可空：v2 快照必须携带标记；v1 迁移保护快照没有标记（null）。v2 备份缺少标记必须显式失败，不得推进基线。
5. **成功基线**
   - 只有备份包通过校验并发布成功后，才把包内快照的 `(database_id, change_sequence)` 写为成功基线。
   - 失败、校验失败、发布前取消、写入取消均不推进基线。
   - 基线只从包内快照标记取得，不从源库当前值取得。
6. **迁移/恢复身份轮换**
   - v1→v2 迁移与任何整库恢复生成新的 `database_id`，并递增 `change_sequence`。
   - 迁移/恢复后立即失效或重建调度基线；基线身份不同视为“有变化”，不得因序号数值接近而误判已备份。
7. **旧状态与未知版本**
   - 旧调度状态文件（含启发式 fingerprint）与当前标记不相等时按“有变化”处理：在符合日备份规则时触发一次备份，并重建基线。
   - 不修改调度状态文件的 `CurrentFormatVersion` 以伪造兼容；未知未来状态版本保守拒绝或保守触发，不静默当作已备份。
   - 丢失基线视为无成功备份，按正常日备份规则处理，不额外增加同日重复备份。
8. **设备设置与草稿不参与**
   - `device-settings.json`、草稿、迁移保护快照不在数据库内，不参与变更标识，也不触发备份（与 [字段策略 ADR](2026-10-28-c3-schema-v2-field-strategy.md) 一致）。
9. **v1 保护快照不推进基线**
   - v1 迁移保护快照的标记为 null；它只用于迁移失败保护/诊断，不是成功备份，不得写入成功基线。

## 后果

**正面**

- 变更检测是确定性的，覆盖分类/标签重命名、关系、外观、设置与布局。
- 成功基线严格对应包内快照；快照期间的新编辑仍待备份，不会误报“已备份”。
- 迁移/恢复后旧基线自动失效，避免序号碰撞导致跳过备份。
- 事务回滚不留下“已变化”假象，减少不必要的同日重复备份。

**负面 / 限制**

- 序号是全局粒度：任何应备份写入都会触发一次备份判断，不能只按便签或分类区分。
- 所有未来写路径都必须记得同事务递增序号；遗漏会导致漏备份。需由仓储/服务层集中封装并通过测试覆盖。
- 分类/标签单写者假设意味着并发管理编辑可能后写覆盖；C3 不做每行版本控制。
- 从快照库读取标记增加一次只读查询；相比“事后读源库”更安全。
- v1 快照没有标记，只能作为保护副本，不能作为成功备份基线。

## 备选方案

- **数据库触发器自动 bump：** 拒绝。行为隐式、迁移/DDL 复杂，且容易在批量写入与恢复中产生意外；显式事务内更新更可审查。
- **对全部表做行级哈希：** 拒绝。扫描成本高，仍需事务内配合，且不能表达“快照内标记”。
- **SQLite `data_version`：** 拒绝。它是连接级/页缓存语义，不持久化，跨进程无效。
- **时间戳判断变化：** 拒绝。时钟回拨、精度和同秒写入不可靠。
- **每表独立序号：** 拒绝。基线与比较复杂度上升，C3 不需要该粒度。
- **快照生成后读源库标记：** 拒绝。会把快照后新编辑误算进已备份基线。
- **恢复后复用原 `database_id`/序号：** 拒绝。旧基线可能误判新库已备份。

## 验证

- 本 ADR 于 Task 1 记录设计；Task 1 未运行变更检测或基线测试，不宣称已通过。
- 计划中的验证（C3 Task 3/5/6）：
  - 写入与序号同事务提交；回滚不递增；读不递增。
  - 同长度分类/标签重命名、颜色/字号/布局/设置/关联变化均被识别。
  - 快照内标记读取；快照期间新编辑保持待备份；缺少标记的 v2 快照备份失败且不推进基线。
  - 失败/发布前取消不推进基线。
  - 迁移/恢复轮换身份后旧基线失效；旧 fingerprint 状态触发一次保守备份。
  - v1 保护快照 null 标记不推进基线。
- C4 启用自动备份前必须复核以上测试通过，并与 [迁移与恢复兼容 ADR](2026-10-28-c3-migration-and-restore-compatibility.md) 的恢复测试一起验收。
