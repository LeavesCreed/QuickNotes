# ADR：C3 schema v2 迁移与 v1/v2 恢复兼容

- **日期：** 2026-10-28
- **状态：** 已接受（随 C3 实施记录）
- **范围：** schema v1→v2 迁移、保护快照、备份包格式、v1/v2 恢复兼容与降级边界
- **相关：** `docs/agent/Agent对接文档_C阶段.md` C3/C4、PRD 11.5–11.8、15.2、17.2、[字段与恢复策略](../agent/C阶段-字段与恢复策略.md)、[B3 快照与包格式 ADR](2026-10-28-b3-consistency-snapshot-and-package.md)、[B5 恢复与回退 ADR](2026-10-28-b5-restore-and-rollback.md)、[C1 启动恢复 ADR](2026-10-28-c1-startup-recovery-state.md)、[C3 字段策略 ADR](2026-10-28-c3-schema-v2-field-strategy.md)

## 背景

C2 及更早版本使用 schema v1，已有用户库和 v1 备份包。C3 需要增加便签外观/布局、`app_settings` 与 `database_meta`。迁移会改变数据库字节；恢复路径既要继续支持 v1 备份包，又不能让半迁移库、未来版本或恢复后的旧基线被误当作正常数据。PRD 11.8 要求迁移前创建保护快照、升级失败不得把半迁移库当正常数据、不得清空便签/分类/标签/布局/设置；PRD 17.2 要求数据模式变化先创建并验证保护快照、失败可回退或安全恢复。

## 决策

1. **schema v2 内容与初始化边界**
   - `notes` 增加 `color_mode`、`color_hex`、`font_size`、`window_left/top/width/height`；新增 `app_settings`、`database_meta`；`PRAGMA user_version=2`。
   - 新建库只创建 v2。`InitializeAsync` 遇到 v1 库抛 `SchemaMigrationRequiredException`，不得就地按 v1 继续写入。
   - 未知未来版本（>2）拒绝，不降级、不猜测、不自动创建空库覆盖。
2. **v1→v2 迁移流程**
   - 启动、取得单实例所有权并在统一写入门内，检测 v1 库。
   - 迁移前执行完整性与外键检查，在数据根 `migration-protection/` 生成并校验**原始 DB 文件**保护快照（非 ZIP），保留且不自动清理；C4 再提供恢复入口/清理策略。
   - 在独立准备区或事务中完成 v1→v2 迁移（新增列/表、种子 `app_settings` 与 `database_meta`），迁移后再次校验完整性、外键、数量与种子值；通过后才允许进入正常写入（Ready）。
   - 迁移失败保持原 v1 库可用，不把半迁移库当作正常数据；允许重试，不得自动删除保护快照或原库。
3. **数据库身份轮换**
   - v1→v2 迁移成功与任何整库恢复都生成新的 `database_id` 并递增 `change_sequence`。
   - 迁移/恢复后重建或失效备份调度基线，避免旧身份/旧序号被误判为相同数据（详见 [变更标识与快照基线 ADR](2026-10-28-c3-change-marker-and-snapshot-baseline.md)）。
4. **备份包格式保持 1**
   - manifest `formatVersion` 保持 1；`schemaVersion` 允许 1 或 2（创建侧写 2，恢复侧校验 1/2）。
   - ZIP 条目仍严格为 `manifest.json` + `notes.db`；不因 schema 升级改变包结构或新增条目。
   - 数据库 schema 版本与备份包格式版本分别管理；未来改变包结构必须另写兼容性 ADR。
5. **恢复兼容矩阵**

| 当前应用 | 当前 DB | 包内 DB schema | 结果 |
|---|---:|---:|---|
| C2（v1 代码） | 1 | 1 | 现有直接恢复路径，C3 不改其行为 |
| C3 | 2 | 2 | 直接预检/恢复；恢复后轮换 DB 身份 |
| C3 | 2 | 1 | 以原 manifest 哈希验证包内原始库 → 暂存库迁移 v1→v2 → 轮换身份 → 按目标哈希切换/核对 |
| C3 | 1 | 1/2 | 正常启动必须先迁移当前库；恢复预检拒绝 v1 当前库，提示使用启动迁移 |
| 任意 | 未知 >2 | 未知 >2 | 拒绝；不降级、不半迁移 |
| C2（v1 代码） | 2 | 任意 | 不支持；v1 代码不得打开 v2 库 |

6. **哈希与切换语义**
   - 对 v1 包：先用原 manifest 哈希验证包内原始库，再迁移暂存库；校验迁移后目标库并记录目标校验值。
   - 切换后按目标校验值核对，**不得**拿迁移后的库直接比原包哈希。
   - 迁移/恢复失败时保持原库与保护副本；失败/取消不得报告成功。
7. **恢复必须已有 v2 当前库**
   - C3 启动完成后当前库必须是 v2。恢复预检不接受 v1 当前库，避免“启动迁移”和“恢复迁移”两条分叉路径；用户需先完成启动迁移再恢复。
8. **安全边界**
   - 迁移、恢复、重建均受同一写入协调与单实例边界控制；不启用 WAL，沿用 rollback journal 与单进程假设。
   - 未知/损坏的恢复状态不猜测成功；保留证据并进入安全入口（沿用 C1 阻断规则）。
9. **v1 保护快照与 v1 备份包的区别**
   - v1 迁移保护快照是本机原始 DB 文件，没有变更标识；不得当作备份包参与留存或作为成功备份基线。
   - v1 备份包仍可按第 5/6 条恢复；恢复成功后包内数据成为当前 v2 库。

## 后果

**正面**

- 只有一条 v1→v2 升级路径；恢复 v1 包复用同一迁移实现，减少分叉。
- 保护快照、目标哈希与失败保留使升级/恢复失败不破坏原数据。
- 包格式保持 1，C3 不必同时变更 ZIP/manifest 解析，降低兼容风险。
- 身份轮换保证恢复/迁移后旧调度基线不会错误跳过备份。

**负面 / 限制**

- 不支持降级：v2 库不能被 C2/v1 代码打开；用户回退旧版本需先恢复 v1 备份或使用外部副本。此边界需在 C7 运行说明中写明。
- 迁移需要额外磁盘空间保存保护快照；C4 前没有自动清理入口。
- v1 备份恢复比 v2 包多一次迁移与目标校验，耗时更长。
- 迁移/恢复测试必须在 C3 Task 4–6 完成；在测试通过前，C4 不应启用自动备份（C3 对接文档要求）。
- 迁移保护快照不自动清理可能占用空间；C4 需提供明确策略，不得删除唯一有效原始数据。

## 备选方案

- **原地、非事务式逐列迁移后继续写入：** 拒绝。部分成功会留下半迁移库，违反 PRD 11.8。
- **把 manifest `formatVersion` 升为 2：** 拒绝。schema 变化不等于包结构变化，会无理由破坏旧读取方兼容。
- **支持 v2→v1 降级：** 拒绝。C3 无无损反向映射，且会丢失外观/设置；只提供升级与恢复。
- **恢复 v1 包时直接以迁移后库比对原包哈希：** 拒绝。字节已变化，必然误报损坏。
- **C3 恢复预检接受 v1 当前库并就地迁移：** 拒绝。会与启动迁移形成两条路径，难以保证阻断与失败回退一致。
- **未知版本自动建空库继续：** 拒绝。违反“不静默初始化空库”和 AGENTS 数据安全规则。

## 验证

- 本 ADR 于 Task 1 记录设计；Task 1 未运行迁移或恢复测试，不宣称已通过。
- 计划中的验证（C3 Task 2/4/6）：
  - schema v2 建库、v1 `InitializeAsync` 拒绝、种子值与 `user_version=2`。
  - v1→v2 成功、迁移失败保持原库、重复启动、取消/中断、未来版本拒绝、保护快照存在且校验通过。
  - v1 包恢复：原 manifest 哈希验证 → 迁移 → 身份轮换 → 目标哈希核对；失败不破坏原库。
  - 兼容矩阵各行与 `formatVersion=1`、`schemaVersion=1/2` 校验。
- C4 启用自动备份前必须复核上述测试与 [变更标识 ADR](2026-10-28-c3-change-marker-and-snapshot-baseline.md) 的基线测试结果。
